This part comes much later. I built a CLI to make the integrated software I'd built easy to use, and alongside it an MCP server that runs over standard input/output. Then I made a VS Code extension to make it easier still.

What I wanted was simple: use our design system and shared components straight from the CLI, and expose them as MCP tools so anyone could pull them in easily.

Something helped enormously along the way: the package structure I'd split out from the start. To explain it, we have to go back to about a week after I joined.

## Walls on day one

A week into the job, I started refactoring the existing frontend source and redesigning its structure from scratch. The first commit to the new repository was on March 13, 2025. From that very first day, it had walls in it: shared packages for components, hooks, styles, and utilities, plus a Storybook to view and tweak those components on their own.

The software task force didn't even exist yet. So why go that far on day one? Here's the honest answer.

## Alone, I'd have just thrown it together

If I'd planned to build this by myself the whole way, I'd have just thrown it together.

What would it matter? Especially now, when AI writes code for you, architecture is close to a luxury if you're working alone. These days I barely type code myself. Someone like me fussing over architecture might even sound a little funny.

And that's right. **Alone**, it doesn't matter.

But software that ties many robots together isn't something one person builds. Many people build it together and keep changing it for a long time. That's exactly where the story changes.

## Rules are uncomfortable. That's why you need them

Separate shared packages from service logic, and your teammates get rules and standards to follow — what goes where, what to reuse, what not to rebuild. The tighter the rules, the more uncomfortable it feels. If you just want to ship one screen fast, those walls look like obstacles.

But over the long run, that discomfort is what lets a team **move like a single body**. Whether you use AI or not.

## What matters more in the age of AI

Coding skill and knowledge still matter. But now that AI writes code, I think something else matters more:

- Can you **design a structure** many people can work in together?
- Have you **experienced, or actually run,** that kind of collaboration process yourself?

For long-term maintenance, separating shared packages from service logic and agreeing on design patterns isn't optional. It's fundamental.

## Back to that day

Now, back to the CLI and the MCP server.

To wrap a design system and shared components as tools, they can't be tangled up with service logic. The separation I'd set up on day one did exactly that job.

The lines drawn on day one came back, much later, in a completely different job.

## How I'd decide now

If the code is just for you, speed beats structure. But if many people will build it for a long time, **the lines you draw on day one decide how fast you can move later.**

AI can write the code, but people still have to decide where that code belongs.
